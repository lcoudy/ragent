# API 错误处理 Runbook

本文补充 `api-response-contract.md`，重点说明接口报错时如何定位责任层并保持前后端行为一致。

## 先确认错误来自哪一层

1. 浏览器是否成功发出请求。
2. 网关或代理是否改写路径、状态码或响应体。
3. Controller 是否完成参数绑定与校验。
4. Service 是否抛出业务异常。
5. 数据库、中间件或模型供应商是否返回下游错误。
6. 前端 service 是否正确解包统一 `Result`。

## 认证与参数错误

认证失效应由统一请求层处理，避免每个页面重复判断。参数错误需要给出字段名、约束和修复方式；日志可以记录请求 ID 与字段信息，但不要打印密码、token、API Key 或完整文件内容。

## 服务端异常

服务端日志至少保留请求或 Trace ID、接口路径、业务对象标识、下游依赖名称、根异常类型和受控摘要。客户端只返回稳定错误码和简洁消息，详细堆栈留在服务端。

## 前端展示

前端应区分登录失效、可修复输入错误、暂时性服务失败和未知异常。页面级提示应保留表单、筛选和编辑上下文。

## 验证清单

- 正常响应仍能统一解包。
- 401/403 不会无限重试。
- 参数错误能定位字段。
- 500 不泄露堆栈或敏感配置。
- SSE 错误事件不会被当作普通完成事件。
